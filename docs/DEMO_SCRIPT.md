# Демонстрация очереди мастера

## Открытый люк на реальном кадре

Откройте [ML-демо](http://127.0.0.1:8767/) после запуска по [инструкции](ML_BENCHMARK.md). На публичном фото покажите область, которую нашёл YOLO26n, и оценку открытого проёма от DINOv2. Затем откройте карточку с панелью «Перепроверка gemini-4-argon» и сравните пояснение с исходным кадром. По кнопке «Новый кадр» можно прогнать отдельное фото через тот же локальный детектор.

На публичных фото координаты отсутствуют. Привязку к реестру покажите на отдельном учебном прогоне.

## Сверка объекта с реестром

Распакуйте `route-demo.zip` из [релиза v0.1.0](https://github.com/coneldiablo/mgts-route-inspector/releases/tag/v0.1.0) в корне проекта. Архив содержит учебный прогон `runs/route-demo` из 118 кадров.

```bash
python -m inspector serve --run runs/route-demo --artifact artifacts/synthetic --port 8765
```

1. Покажите карточку с ID из реестра и положение объекта на схеме.
2. В фильтре привязки выберите карточки для сверки. На `KKS-0003__v1` показаны GPS машины и два объекта-кандидата из учебного реестра. Объясните, какой внешний признак позволит мастеру подтвердить нужный ID при наличии реальных данных.
3. Привяжите карточку к одному из кандидатов. Она появится на схеме. Статус замечания можно подтвердить отдельной кнопкой.
4. Выгрузите GeoJSON для карты или CSV с решением, причиной и источником привязки.

Фотографии, координаты и записи реестра в этом прогоне учебные. Оценку качества на маршрутах МГТС проводят после получения целевой выборки.

## Показ за три минуты

1. **0:00–0:30.** Откройте готовый публичный прогон по [инструкции запуска](../README.md#быстрый-старт). Объясните цель показа. Мастер проверяет, достаточно ли хорошо видна крышка. Порог отбирает кадры для такой проверки. Открытый проём требует отдельной разметки состояния.
2. **0:30–1:05.** Выберите «Все объекты» и поищите `MHH-00109`. На снимке видна круглая крышка. Затем найдите `MHH-00239` — в кадр попало колесо. Сопоставьте исходное изображение с действием, которое предлагает карточка. Координаты и время на этих публичных фото отсутствуют.
3. **1:05–1:45.** Откройте `MHH-00183`. Виден тёмный прямоугольный элемент. Файл размечен `manhole`, гибрид уверенно отправляет его на проверку. Мастер может отклонить предложение и записать причину. Покажите этот же ID и решение в CSV прогона.
4. **1:45–2:15.** Перейдите к «Нужен кадр», откройте `MHH-00066`. Контраста недостаточно, система запрашивает повторный кадр. Покажите заранее выбранное фото через «Загрузить новый кадр». Такая загрузка даёт отдельный предпросмотр.
5. **2:15–3:00.** Измените порог и верните порог прогона. Покажите [результаты двух моделей](AUDIT.md). Зафиксируйте, какое решение поддерживает метрика. В выборке каждый ID соответствует одному фото. Историю разных ракурсов одного люка можно отдельно показать на синтетическом стенде.

## Что отвечать про готовность

- **Данные.** У поставщика есть классы `manhole` и `void`. В просмотренных примерах второго класса встречаются улица, машина и стена. Группа размеченных открытых проёмов требуется отдельно.
- **Модель.** Сравнение проведено с классическими признаками на тех же изображениях и с тем же фильтром качества. Время полного прогона записано в `runs/public/summary.json`.
- **Проверка на маршруте.** Нужны фотографии с подтверждённой видимостью и состоянием люка, привязка к объекту и визиту, согласованный с мастером лимит ложных карточек. Эксплуатационный эффект измеряется временем ручного разбора и числом пропусков.
- **Новый район или сезон.** Порог фиксируется на обучающей части. Для проверки переноса нужна отдельная подборка маршрутов с реальными ID объектов.

## Если данных МГТС не будет или они другие

Порядок на площадке:

1. Прочитать обязательные поля и критерии. Посчитать **уникальные объекты**, а не кадры.
2. Посмотреть 10–20 полноразмерных кадров каждого класса. Проверить, виден ли признак
   на реальном масштабе.
3. Если размечено только «норма/дефект» — оставить бинарную очередь.
   Если несколько дефектов — многоклассовый режим, но карточки по каждому признаку.
4. Если объектов мало (<10) — не заявлять полноту; показать механику и список ошибок.
5. Если есть только норма — переключить историю на режим аномалий и честно назвать
   полноту неизмеренной.
6. Если данные — видео/общие планы — сначала детектор/кадрирование; иначе не смешивать
   ошибки.

## План 180 минут

| Минуты | Действие | Результат |
|---|---|---|
| 0–20 | ТЗ, поля, классы, данные, вопросы наставнику | один сценарий и метрика |
| 20–45 | manifest, 10–20 кадров, проверка признака, split по объектам | решение: бинарно/мультикласс/аномалии |
| 45–80 | обучение, OOF, baseline, порог | первый отчёт и очередь |
| 80–110 | интерфейс на реальных кадрах, отказ, повторы | сквозной путь |
| 110–135 | ошибки, условия, метрики, ограничения | честные цифры |
| 135–160 | тестовые изображения, экспорт, репетиция | результат в требуемом формате |
| 160–180 | защита, ответы, резервный прогон | готовность |

## Роли

- **Ведущий по решению:** вопросы наставнику, определение признака, границы вывода,
  ответы про ремонт и регламент.
- **Ведущий по данным и модели:** manifest, split, обучение, порог, метрики, ошибки.
- **Ведущий по демонстрации:** интерфейс, новый файл, повторы, экспорт, тайминг.

Все трое должны уметь запустить `python -m inspector run` и объяснить `eval.md`.
